## Project status

This is a freshly scaffolded Flutter application (`fresh_keep_frontend`) — the frontend client for the "Fresh Keep" system. At present `lib/main.dart` contains only the default `MaterialApp` starter widget; There are no tests.

Supported platforms: Android, iOS, web, macOS, Linux, Windows (all platform folders are present and generated by `flutter create`).

## Commands

`flutter` in this environment is aliased to `fvm flutter` (Flutter Version Management), so plain `flutter <cmd>` picks up the project-pinned SDK version automatically.

- Install dependencies: `flutter pub get`
- Run the app (device/emulator/web): `flutter run`
- Static analysis / lint: `flutter analyze` (rules come from `analysis_options.yaml`, which just includes `package:flutter_lints/flutter.yaml`)
- Run all tests: `flutter test`
- Run a single test file: `flutter test test/path/to/some_test.dart`
- Format code: `dart format .`
- Build release artifacts: `flutter build apk` / `flutter build ios` / `flutter build web` / etc.

## Backend API contract

`api_contract.md` documents the authentication API of the backend this app talks to (a separate Spring Boot service, not in this repo). It covers `POST /api/v1/auth/register/user`, `POST /api/v1/auth/register/admin`, and `POST /api/v1/auth/login` under base path `api/v1/auth`, including request/response shapes, the `ProblemDetail` (RFC 7807) error format, and the JWT bearer-token security model (stateless, no cookies; `Authorization: Bearer <token>`; role-gated admin registration). Consult this file before implementing any auth-related networking code so request/response models and error handling match the backend exactly.

## Implementation Reference & Standards

### Primary Reference
- **Source of Truth**: For ALL implementation tasks, you MUST consult and strictly follow the patterns, code structures, and best practices defined in: `.agents/skill/flutter-expert`.
- **Consistency**: Ensure all new code aligns with the architecture and snippets provided in that skill file.

### Architecture: Clean Architecture
All code must follow **Clean Architecture** principles, strictly separating concerns into three layers:
1.  **Domain Layer**: (Core) Entities, Use Cases, and Repository Interfaces. Zero dependencies on other layers.
2.  **Data Layer**: Repository Implementations, Models (DTOs), and Data Sources (API). Models must include `toEntity()` and `fromEntity()`.
3.  **Presentation Layer**: UI (Widgets/Pages) and State Management logic.

### State Management: BLoC & Cubit
- **Primary Choice: BLoC**. Use BLoC for any logic involving complex events, multiple state transitions, or side effects.
- **Secondary Choice: Cubit**. Use Cubit ONLY for simple, local UI states (e.g., toggles, simple form validation without API calls).
- **Refactoring**: If a Cubit grows in complexity, refactor it immediately to a BLoC.
- **Organization**: Place BLoCs/Cubits in: `lib/features/feature_name/presentation/bloc/`.

### Coding Style Guidelines
- **Naming**: BLoC events must use "Past Tense" (e.g., `LoginSubmitted`, `ProfileUpdated`).
- **Immutability**: All States must be immutable using `equatable` or `freezed`.
- **Dependency Injection**: Use `get_it` to provide Use Cases and Repositories to BLoCs.
- **UI Separation**: Widgets must never contain business logic; they only dispatch events and listen to states.
